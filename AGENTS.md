# Limitless Creators: правила работы для Codex

## Назначение проекта

Это исходная Gulp-вёрстка сайта Limitless Creators. Она используется как визуальный и компонентный эталон при доработке действующей темы WordPress.

Текущая задача проекта — развивать коммерческие страницы, статьи и кейсы без потери существующего дизайна, URL, SEO-структуры и управляемости через WordPress.

## Структура

- `app/*.html` — статические шаблоны страниц.
- `app/services-taxonomy-dev.html` — эталон страницы категории «Разработка».
- `app/sass/main.sass` — основные стили.
- `app/sass/_media.sass` — адаптивные стили.
- `app/js/common.js` — исходный JavaScript.
- `app/css/main.min.css` и `app/js/scripts.min.js` — сгенерированные файлы. Не редактировать вручную.
- `dist/` — результат сборки. Не использовать как исходник и не коммитить.

## Команды

```bash
npm ci
npm run lint:project
npm run dev
npm run build
```

Перед завершением задачи обязательно выполнить `npm run lint:project` и `npm run build`.

## Общие ограничения

1. Не менять несвязанные страницы, стили и скрипты.
2. Не переписывать существующий компонент без необходимости.
3. Не добавлять новый фреймворк, сборщик или библиотеку без прямой причины.
4. Сохранять текущую BEM-подобную систему классов и визуальный язык.
5. Все изменения должны работать на мобильных, планшетах и десктопах.
6. Не редактировать минифицированные файлы вручную.
7. Не добавлять `node_modules` и `dist` в Git.
8. Не использовать вымышленные кейсы, цифры, отзывы, результаты или состав команды.
9. Не обещать рост заявок, продаж, трафика или позиций без подтверждённых данных.

## Browser QA и временные артефакты

### Хранение QA-артефактов

- Не сохранять скриншоты, временные browser scripts, patch-файлы, логи и результаты проверок напрямую в общий системный `%TEMP%`.
- Для каждого проекта использовать локальную исключённую из Git папку `.qa-artifacts/<task-slug>/`.
- Для каждой задачи использовать отдельную вложенную папку с понятным названием, например `.qa-artifacts/live-search/`, `.qa-artifacts/portfolio-architecture/` или `.qa-artifacts/about-page/`.
- Не складывать артефакты разных задач в одну общую папку.
- Перед повторной проверкой очищать только папку соответствующей QA-задачи.
- Не удалять произвольные файлы из `%TEMP%`.
- Не удалять файлы других приложений, проектов или неизвестного происхождения.
- После завершения проверки удалять временные QA-артефакты задачи, если пользователь явно не попросил их сохранить.
- Не использовать локальные временные пути к скриншотам как постоянные материалы проекта.
- Не добавлять `.qa-artifacts/` в Git.

### Browser QA

- Использовать существующий локальный сервер, если он уже запущен.
- Не запускать дополнительный сервер без необходимости.
- Использовать один browser context.
- Использовать одну вкладку.
- Переиспользовать вкладку для всех URL и viewport.
- Не создавать отдельный context или вкладку для каждого скриншота.
- Не запускать параллельные browser-проверки.
- После проверки закрывать страницы и contexts, созданные автоматизацией.
- Не завершать пользовательские процессы Chrome.
- Не удалять и не изменять пользовательские профили Chrome.
- Сохранять только действительно необходимые скриншоты.
- В итоговом отчёте перечислять созданные артефакты и сообщать, были ли они удалены.

### Временные скрипты

- Временные скрипты для QA хранить внутри `.qa-artifacts/<task-slug>/`, а не в `%TEMP%`.
- Если скрипт становится постоянной проверкой проекта, переносить его в `scripts/`, давать понятное имя и добавлять в Git отдельным осознанным изменением.
- Не оставлять одноразовые `.js`, `.cjs`, `.mjs`, `.patch`, `.log`, `.out` и `.err` после завершения задачи.

## Обязательная матрица адаптивной проверки

Для любых визуальных изменений страниц и компонентов обязательно проверять:

- 1920 px — основной desktop и проверка максимальной ширины контейнера;
- 1440 px — средний desktop;
- 1024 px — небольшой desktop / планшет landscape;
- 768 px — планшет;
- 390 px — мобильный экран.

1920 px нельзя заменять проверкой на 1440 px.

На 1920 px дополнительно проверять:

- совпадение границ контейнера у header, main и footer;
- отсутствие чрезмерно длинных строк;
- баланс колонок;
- отсутствие лишней пустоты;
- корректную максимальную ширину секций;
- отсутствие растягивания карточек и кнопок;
- визуальный ритм между секциями.

Для значительных изменений обязательно готовить минимум:

- скриншот 1920 px;
- скриншот 390 px;
- дополнительные скриншоты на промежуточных ширинах, если меняется адаптив.

Перед созданием скриншотов:

- закрывать или принимать cookie-уведомление, если оно перекрывает проверяемую область;
- закрывать открытое мобильное меню;
- не оставлять модальные окна и служебные панели поверх страницы.

## Правила WordPress-интеграции

Когда в репозиторий будет добавлена действующая тема WordPress:

1. Производственным источником становится тема WordPress; статическая вёрстка остаётся эталоном интерфейса.
2. Не менять публичные URL и типы записей без отдельного задания.
3. Данные выводить из WordPress и ACF, а не дублировать статически.
4. Если поле, изображение, ссылка, элемент списка или блок не заполнены, не выводить элемент и не подставлять статический fallback.
5. Поля, без которых блок не может работать корректно, делать обязательными в ACF.
6. Экранировать вывод: `esc_html()`, `esc_attr()`, `esc_url()`, `wp_kses_post()` по назначению.
7. Для циклов и запросов восстанавливать глобальные данные через `wp_reset_postdata()`.
8. Не хранить секреты, SMTP-доступы, ключи и пароли в репозитории.
9. Не править плагины и ядро WordPress.
10. Изменения ACF оформлять управляемо: через PHP-регистрацию полей или синхронизируемый `acf-json`, в зависимости от текущей архитектуры темы.

## Страница категории услуг

Для категории «Разработка» нужно сохранить текущую шапку, автоматический вывод услуг, алгоритм, FAQ и стилистику, но превратить страницу в управляемый коммерческий хаб.

Целевые секции:

1. Шапка с H1, описанием, ценой, пояснением и двумя CTA.
2. Основные направления разработки — управляемые карточки со ссылками на существующие услуги.
3. Полный список услуг — автоматический вывод, управляемые группа, порядок и видимость.
4. Состав работ.
5. Технологии.
6. Выбранные кейсы.
7. Этапы работы.
8. Ориентиры стоимости.
9. Короткий блок о составе специалистов без неподтверждённых ролей.
10. FAQ.

Новые секции должны быть необязательными: пустой блок не выводится.

## Формат работы

Перед крупным изменением:

1. Изучи связанные HTML, SASS, JavaScript и шаблоны WordPress.
2. Кратко перечисли файлы, которые планируешь менять.
3. Выполни изменение небольшим связанным набором правок.
4. Запусти проверки и сообщи точный результат.
5. Перечисли изменённые файлы и оставшиеся ограничения.
